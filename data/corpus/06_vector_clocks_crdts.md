# Causality Tracking with Vector Clocks and Conflict-Free Replicated Data Types (CRDTs)

## Vector Clocks for Distributed Causality
In multi-master active-active clusters where concurrent writes occur across divergent geographic regions, physical wall-clock timestamps are susceptible to clock drift and synchronization inaccuracies. AetherDB employs Vector Clocks to establish partial ordering and detect causal relationships without physical time dependencies. A vector clock is represented as an array or map of tuples `VC = {node_id_1: counter_1, node_id_2: counter_2, ..., node_id_k: counter_k}`. When node $i$ modifies an object, it increments its own component `VC[node_i] = VC[node_i] + 1`. An event $A$ causally precedes event $B$ ($A \prec B$) if and only if for all nodes $k$, $VC_A[k] \le VC_B[k]$, and there exists at least one node $j$ such that $VC_A[j] < VC_B[j]$. If neither precedes the other, a concurrent conflict is flagged.

## Last-Write-Wins (LWW) Clock Skew Vulnerability
Many traditional NoSQL databases resolve concurrent write conflicts using the Last-Write-Wins (LWW) policy based on physical timestamps (e.g., NTP-synchronized wall clocks). However, NTP clock skew—even when controlled within tens of milliseconds—can cause a silent data loss anomaly known as the `LWW Clock Inversion Trap`. A write executed later in true physical time by node $A$ may carry an earlier NTP timestamp than an outdated write from node $B$ whose clock runs ahead. As a result, the obsolete write permanently overwrites the newer write without raising an error.

## Conflict-Free Replicated Data Types (CRDTs)
To eliminate manual conflict resolution and LWW data loss, AetherDB natively implements state-based Convergent Replicated Data Types (CvRDTs) and operation-based Commutative Replicated Data Types (CmRDTs):
1. **PN-Counter (Positive-Negative Counter)**: Maintains two independent monotonic sub-counters: $P$ for increment operations and $N$ for decrement operations. The net value is computed as $\sum P - \sum N$. Merge operations take the element-wise maximum: $\text{merge}(P_1, P_2) = (\max(P_1[i], P_2[i]))$.
2. **Observed-Remove Set (OR-Set)**: Represents an additive-remove set where items can be inserted and deleted repeatedly. Each added item is tagged with a globally unique timestamp or UUID `(item, tag)`. A delete operation adds the active tags associated with that item to an internal tombstone set. An item is deemed present if its addition tags minus its tombstone tags is non-empty. Merge takes the union of element sets and the union of tombstone sets, guaranteeing commutativity, associativity, and idempotence.
