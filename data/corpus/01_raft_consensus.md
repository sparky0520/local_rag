# Raft Consensus Protocol Specification

## Core State Machine and Node Roles
In AetherDB, distributed state machine replication is coordinated by the Raft consensus protocol. Each cluster node occupies one of three distinct mutually exclusive roles: Follower, Candidate, or Leader. Under steady-state conditions, exactly one Leader coordinates log replication across all nodes in the cluster. Followers remain passive, responding solely to incoming remote procedure calls from Leaders and Candidates. If a Follower receives no communication within a randomized election timeout window, it transitions to the Candidate state and initiates a new election round.

## Election Timouts and Split-Brain Prevention
To prevent split-vote deadlocks where multiple candidates partition the ballot, AetherDB enforces randomized election timeouts. The parameter `HEARTBEAT_INTERVAL_MS` is statically configured to 150 milliseconds, while the follower election timeout is dynamically drawn from a uniform distribution bounded by `ELECTION_TIMEOUT_MIN_MS` (300 ms) and `ELECTION_TIMEOUT_MAX_MS` (600 ms). A candidate node increments its internal `current_term` counter, votes for itself, and broadcasts `RequestVoteRPC` messages to all cluster peers. A candidate becomes the legitimate Leader only upon acquiring affirmative votes from a strict quorum representing a majority of nodes: `(N / 2) + 1`. This strict majority quorum guarantees that no two leaders can ever be elected in the same term, thereby eliminating split-brain anomalies under arbitrary network partitions.

## Log Replication and AppendEntries RPC
Once established, the Leader processes all client write operations. For each write command, the Leader appends a new `LogEntry` containing the command, the current term number, and a monotonically increasing `log_index`. The Leader then issues `AppendEntriesRPC` requests to all follower nodes. Followers verify log continuity using the `prevLogIndex` and `prevLogTerm` fields. If a follower detects a mismatch in its local log history, it rejects the `AppendEntriesRPC`, prompting the Leader to decrement `nextIndex` for that follower and retransmit until a common ancestor log entry is established.

## Commit Invariants and Log Compaction
An entry is deemed committed once it is successfully replicated onto a majority quorum of cluster nodes. Once committed, the Leader advances its internal `commit_index` and applies the command to its local state machine, subsequently notifying followers via the `leaderCommit` field in consecutive heartbeat packets. To prevent unbounded log growth, AetherDB implements snapshot-based log compaction. When the log size surpasses `MAX_RAFT_LOG_SIZE_MB` (512 MB), the state machine serializes its entire state to disk, discarding preceding log entries and retaining only the snapshot index and term metadata.

## Joint Consensus Configuration Membership Changes
Dynamic cluster reconfiguration (adding or removing nodes) is executed via a two-phase Joint Consensus protocol. Rather than switching cluster configurations atomically—which risks overlapping majorities and split-brain—the Leader enters an intermediate transitional configuration `C_old,new`. While operating in `C_old,new`, log entries must achieve independent majority agreement from both the legacy configuration group `C_old` and the incoming configuration group `C_new`. Once the `C_old,new` entry commits, the Leader safely broadcasts the definitive configuration `C_new`.
