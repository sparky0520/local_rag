# Write-Ahead Log (WAL) Durability and ARIES Crash Recovery

## Write-Ahead Logging and Group Commit
In AetherDB, durability is guaranteed by the Write-Ahead Log (WAL) before any data modification is reflected in volatile memory buffers or data files. The fundamental WAL protocol invariant dictates that log records describing a change must be flushed to non-volatile storage (`fsync`) prior to writing the modified dirty pages to disk. To prevent `fsync` system calls from becoming an I/O bottleneck on rotational or NVMe media, AetherDB implements **Group Commit**. Incoming write transactions append their log entries to a shared memory buffer and wait on a completion future. A dedicated WAL flushing thread delays for a tunable window `wal_sync_delay_ms = 5` (or until the buffer accumulates `wal_group_commit_size_kb = 64`), issuing a single coalesced `fsync` call that simultaneously commits dozens of parallel client transactions.

## Log Sequence Numbers (LSN) and Checkpointing
Every WAL record is tagged with a strictly monotonically increasing 64-bit integer: the Log Sequence Number (`LSN`). Each page in memory and on disk also records the `page_lsn` corresponding to the latest update applied to that page. To accelerate recovery following an unexpected crash or power failure, AetherDB runs a continuous background **Fuzzy Checkpointer**. Rather than flushing all dirty pages at once (which causes severe I/O stalls), the fuzzy checkpointer records the current minimum `LSN` of unwritten dirty pages in a checkpoint descriptor file, guaranteeing that log records preceding `checkpoint_min_lsn` can be safely archived.

## ARIES Recovery Algorithm
Upon node reboot following a crash, AetherDB executes the three-phase ARIES (Algorithm for Recovery and Isolation Exploiting Semantics) protocol:
1. **Analysis Phase**: Scans the WAL forward starting from the last valid checkpoint record up to the end of the log. It reconstructs the active transaction table (identifying transactions that were in flight when the crash occurred, termed `losers`) and the dirty page table (identifying dirty pages that may not have been written to disk).
2. **Redo Phase (Repeating History)**: Scans the WAL forward from the minimum `rec_lsn` found in the dirty page table. It reapplies all logged operations—both committed transactions and loser transactions—to return the database state to the exact instant of the crash. If `page_lsn >= log_record_lsn`, the operation is skipped, guaranteeing idempotency.
3. **Undo Phase**: Scans the WAL backward to roll back all operations executed by loser transactions. For each undone operation, the engine writes a Compensation Log Record (`CLR`) containing an `undo_next_lsn` pointer, ensuring that if a subsequent crash occurs during undo, previously undone actions are never undone twice.
