# Log-Structured Merge Tree (LSM) Storage Engine Architecture

## MemTable and Write Buffer Mechanics
AetherDB leverages a Log-Structured Merge Tree (LSM-Tree) as its core persistent storage engine for high-throughput write workloads. All incoming mutations (inserts, updates, and deletes) are initially appended sequentially to an append-only Write-Ahead Log (WAL) on disk for crash durability and simultaneously buffered in an in-memory `MemTable` implemented as a concurrent lock-free SkipList. The active MemTable accepts writes until reaching the threshold configured by `memtable_size_mb = 64`. Once this threshold is exceeded, the active MemTable is converted to an immutable read-only MemTable, and a fresh active MemTable is instantiated. A background flush thread serializes the immutable MemTable to disk as an immutable Level 0 (`L0`) Sorted String Table (`SSTable`).

## SSTable On-Disk Format and Block Indexes
Each SSTable comprises a sequence of compressed data blocks (typically 4 KB each) sorted lexicographically by key, followed by an index block, a filter block (Bloom filter), and a fixed-size footer. The index block maintains pointers and key boundaries for each data block, allowing binary search without scanning the entire file. When servicing a point lookup, the engine inspects the active MemTable, followed by any immutable MemTables, and finally searches the SSTables on disk from the newest level to the oldest level.

## Write Stall and Backpressure Control
When the rate of client writes significantly outpaces background disk flush or compaction throughput, the number of L0 SSTables escalates. Because L0 SSTables contain overlapping key ranges, read amplification degrades rapidly. To defend against runaway read latencies, AetherDB introduces progressive write throttling. When the count of L0 SSTables reaches `LSM_MEMTABLE_STALL_THRESHOLD` (set to 12 files), client write threads are forcibly delayed by 1 millisecond per mutation. If L0 count exceeds `LSM_MEMTABLE_STOP_THRESHOLD` (set to 20 files), all incoming writes are completely frozen until background compaction reduces the L0 file count below the recovery threshold.

## Compaction Strategies: Leveled vs Size-Tiered
AetherDB supports two primary compaction strategies: `LeveledCompactionStrategy` and `SizeTieredCompactionStrategy`. Leveled Compaction organizes SSTables into fixed levels ($L1, L2, \dots, L_N$), where each level has a capacity 10 times larger than the previous level ($L_{i+1} = 10 \times L_i$). Except for L0, all SSTables within any level $L_k$ have mutually disjoint, non-overlapping key ranges. Leveled Compaction guarantees low read amplification ($O(1)$ SSTables per level) and low space amplification (~10%), but exhibits high write amplification ($10\times$ to $30\times$). In contrast, Size-Tiered Compaction groups SSTables of comparable sizes and compacts them into larger tables, minimizing write amplification for append-heavy workloads at the expense of higher temporary space amplification (up to 50% extra disk space).

## Deletion Semantics and Tombstone Compaction
In an LSM storage engine, record deletion is not executed as an in-place disk erasure. Instead, a deletion is recorded as a write operation containing a special marker known as a `Tombstone`. The tombstone masks older versions of the key residing in lower SSTable levels. Consequently, deleting records temporarily increases disk space consumption rather than freeing it. Disk space reclamation only occurs during background compaction when the tombstone and the shadowed obsolete data are merged and purged, provided the tombstone has aged beyond `tombstone_compaction_interval_seconds` (set to 86,400 seconds / 24 hours) to prevent resurrected data across distributed replicas.
