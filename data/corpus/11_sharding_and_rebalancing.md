# Consistent Hashing, Shard Placement, and Dynamic Rebalancing

## Consistent Hashing with Virtual Nodes (Vnodes)
AetherDB partitions the keyspace across cluster storage nodes using consistent hashing over a 64-bit integer ring $[0, 2^{64}-1]$. To prevent non-uniform data distribution and hotspots caused by sparse random node placement on the ring, AetherDB introduces **Virtual Nodes (Vnodes)**. Each physical server is assigned `vnodes_per_node = 256` distinct token locations on the ring generated by hashing the node identifier with sequential seeds `hash(node_id + "#" + vnode_index)`. When a key is inserted, its MurmurHash3 64-bit digest is calculated, and the coordinator locates the first vnode clockwise from the key hash on the token ring.

## Partition Placement and Fault Domain Diversity
To withstand catastrophic hardware failures, replicas for each shard must be distributed across independent physical failure boundaries. AetherDB enforces a rack-aware and availability-zone-aware placement topology. When replication factor $N=3$, the placement engine selects the primary vnode owner and subsequent distinct physical servers located in separate availability zones (e.g., `us-east-1a`, `us-east-1b`, `us-east-1c`) and distinct top-of-rack (ToR) network switches. This guarantees survivability even if an entire datacenter power transformer or rack switch suffers complete loss of power.

## Online Dynamic Shard Migration and Dual-Writing
When adding a new physical node to an existing cluster or decommissioning an obsolete server, AetherDB rebalances shards dynamically without downtime or read disruption:
1. **Token Assignment**: The coordinator computes the target vnode allocations for the new node and identifies source donor nodes whose token ranges will be transferred.
2. **Dual-Write Phase**: Client write requests for the migrating range are routed concurrently to both the donor node and the recipient node.
3. **Catch-Up Streaming**: The donor node streams historical SSTables and active MemTable snapshots to the recipient node using rate-limited background TCP streams capped by `migration_max_bandwidth_mb = 120`.
4. **Cutover Atomic Switch**: Once the recipient node's replication lag falls below `migration_cutover_max_lag_ms = 50`, the coordinator updates the cluster routing table via Raft, donor nodes release the token ranges, and the recipient node officially assumes primary ownership.
